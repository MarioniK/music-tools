# AGENTS.md

Инструкции для AI-агентов и Codex при работе с репозиторием `music-tools`.

## Язык общения

- Всегда отвечать пользователю на русском языке.
- Документацию, отчёты, комментарии и docstrings для проекта писать на русском языке, если задача явно не требует английский.
- Технические идентификаторы, имена файлов, переменные, функции, классы и API-контракты сохранять в стиле текущего кода.

## Источник истины

- Основной репозиторий: `MarioniK/music-tools`.
- Не считать live-дерево сервера доступным автоматически.
- Если нужен анализ фактического кода, опираться только на:
  1. код и фрагменты, присланные пользователем;
  2. локальное дерево, если Codex реально выполняется в `/opt/music-tools`;
  3. GitHub-репозиторий, если он доступен через инструменты.
- Не делать вид, что файлы были проверены, если они не были прочитаны.

## Контекст проекта

`music-tools` — монорепозиторий с двумя отдельными сервисами:

- `tidal-parser` — основной API, orchestration и внешние интеграции;
- `genre-classifier` — сервис классификации аудио.

Сервисы взаимодействуют по HTTP внутри Docker network.

Это не единое runtime-окружение.

У сервисов отдельные директории и отдельные Docker Compose-конфигурации.

Нельзя предполагать наличие общего Compose-файла в корне репозитория.

## Pipeline

TIDAL -> parse_tidal -> Discogs -> MusicBrainz -> audio classifier -> merge -> cache

## Service scope

Если задача относится только к `genre-classifier`, работать только в:

`/opt/music-tools/genre-classifier`

Если задача относится только к `tidal-parser`, работать только в:

`/opt/music-tools/tidal-parser`

Для git-действий на уровне репозитория использовать:

`/opt/music-tools`

Docker Compose команды выполнять только из директории конкретного сервиса.

Не запускать Docker Compose из корня monorepo, если пользователь явно не сказал, что там есть общий Compose.

Не трогать соседний сервис без явной причины.

## Границы изменений

- Не менять внешний API без явного запроса.
- Не менять contract сервисов без явного запроса.
- Не менять response shape без явного запроса.
- Не менять cache-логику без явного запроса.
- Не менять synchronous HTTP boundary между сервисами без явного запроса.
- Не менять production defaults без явного запроса.
- Не менять provider/default logic без явного запроса.
- Не менять model/audio/dependency/runtime-файлы без явного запроса.
- Не трогать templates без необходимости.
- Не добавлять зависимости без необходимости.
- Не делать широкий redesign, если задача сформулирована как локальный safe refactor.
- Не смешивать соседние roadmap-этапы в одном изменении.
- Не тащить элементы следующего этапа в текущий safe-slice.
- Предпочитать минимальные, безопасные и rollback-friendly изменения.
- При неопределённости выбирать migration-safe решение, а не лишнюю архитектурную красоту.

## Архитектурные правила

- Уважать текущую архитектуру проекта.
- Не добавлять новый backend, новую БД, новый framework или новый runtime без отдельного архитектурного решения.
- Не вводить service/repository/dto/exceptions/validators-структуру механически.
- Добавлять новые слои только если они естественно нужны текущей задаче и не ломают существующую архитектуру.
- Соблюдать Single Responsibility.
- Не вводить абстракции заранее.
- Dependency Inversion применять только там, где уже есть реальная граница зависимостей или она нужна задаче.
- Предпочитать явные вызовы скрытой магии.
- Избегать циклических импортов.
- Для type hints при необходимости использовать `TYPE_CHECKING`.
- Учитывать async/sync контекст.
- Не блокировать event loop тяжёлыми синхронными операциями без необходимости.

## Стиль кода

- Соблюдать PEP 8 и текущий стиль проекта.
- По возможности добавлять type hints для параметров и возвращаемых значений.
- Избегать `Any`, если можно использовать конкретный тип без усложнения.
- Новые публичные классы и функции снабжать docstrings на русском языке, если это помогает пониманию.
- Комментировать только сложную или неочевидную логику.
- Не добавлять декоративные комментарии.
- Код должен оставаться читаемым.
- Не переименовывать существующие сущности без необходимости.
- Не делать косметический рефакторинг вместе с функциональным изменением.

## Данные и безопасность

- Санитизировать пользовательский ввод.
- Не использовать небезопасные прямые SQL-запросы.
- Если SQL когда-либо появится, использовать параметризованные запросы или существующий безопасный слой доступа.
- Не логировать чувствительные данные: токены, пароли, персональные данные, секреты.
- Для внешних API учитывать таймауты, ошибки, retry/rate limit-поведение, если это уже принято в сервисе.
- Не менять cache-поведение без явного запроса.

## Логирование

- Использовать существующий общий logger проекта.
- Логировать осмысленные диагностические события.
- Не дублировать логи.
- Не создавать лишний шум.
- Использовать уровни `DEBUG`, `INFO`, `WARNING`, `ERROR` по смыслу.
- Не логировать чувствительные данные.
- Сохранять `request_id` / correlation ID там, где он уже используется.
- Логи должны помогать понять состояние pipeline.

## Docker / build / test

- Перед командами определить, к какому сервису относится задача.
- Не давать и не выполнять Compose-команды из корня monorepo без явного разрешения.
- Для `genre-classifier` использовать `/opt/music-tools/genre-classifier`.
- Для `tidal-parser` использовать `/opt/music-tools/tidal-parser`.
- Не запускать rebuild, up, exec, logs, smoke-check или тесты второго сервиса без явной причины.
- Не смешивать operational steps двух сервисов в одном плане, если задача локальная.
- Не запускать тяжёлые проверки, inference, ONNX, TensorFlow, parity comparison или `/classify` без явного разрешения.
- Если задача документационная, не запускать Docker и тесты без отдельной причины.

## Codex workflow

Базовый процесс:

1. Сделать только запрошенное изменение.
2. Не делать commit, tag, push без отдельной команды пользователя.
3. После выполнения создать временный markdown-отчёт в корне репозитория.
4. Временный отчёт не является частью проекта и не должен попадать в commit.
5. Перед commit временный отчёт должен быть удалён отдельным cleanup-шагом.

Временный отчёт должен содержать:

- краткое описание;
- список изменённых файлов;
- `git status --short`;
- `git diff --stat`;
- релевантные diff-фрагменты.

Рекомендуемое имя временного отчёта:

`AGENT_REPORT.md`

## Git workflow

- Базовый режим: Keep -> Build -> Test -> Commit.
- Не делать commit без отдельной команды пользователя.
- Не делать tag без отдельной команды пользователя.
- Не делать push без отдельной команды пользователя.
- Использовать точечный `git add` для важных изменений.
- Для небольших safe-slice изменений допустима работа в `main`, если пользователь это разрешил.
- Для широких, рискованных или экспериментальных изменений сначала предложить отдельную ветку.
- Предпочитать серию маленьких коммитов вместо одного большого.
- Каждый шаг должен быть легко откатываемым.
- Cleanup, staging, commit, push, tag, release делать отдельными prompts после проверки.
